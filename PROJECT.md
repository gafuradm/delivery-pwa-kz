# 📘 QazconHub — Детальное документ-описание проекта

> **Полное техническое описание** цифровой платформы логистического терминала ТОО «QazconHub».
> Документ охватывает архитектуру, стек технологий, схему базы данных, все API-эндпоинты, ролевую модель, структуру фронтенда, PWA-возможности, безопасность и развёртывание.

## 1. Обзор проекта

**QazconHub** — это современное **PWA-приложение** (Progressive Web App) для комплексного управления логистическим терминалом. Платформа автоматизирует ключевые операционные процессы терминала:

- 📦 **Контейнерные операции** — учёт, размещение и отслеживание контейнеров.
- 📥📤 **Завоз и вывоз** — документы терминала по бумажным формам со сквозной нумерацией,
  жизненным циклом статусов, пропуском по документу и вывозом по завозу.
- 🧾 **Расходные накладные** — шапка с доверенностью и получателем, строки с контейнерами,
  грузом, количеством и складом, создание вывоза по строке.
- 🗂️ **Справочники** — склады, контрагенты и ответственные лица для форм документов.
- **Железнодорожные пути (ППЖТ)** — управление путями и вагонами.
- 🏗️ **Спецтехника** — учёт кранов, погрузчиков и тягачей.
- 🚛 **Транспорт и пропускной режим** — въезд/выезд, OCR-распознавание номеров, шлагбаумы, пропуска.
- 🔢 **Электронная очередь** — запись водителей и назначение слотов.
- 📋 **Заявки клиентов** — создание и обработка заявок.
- 📜 **Журнал действий и отчёты** — аудит и PDF-отчёты.

Ключевая особенность — **единая роль-ориентированная панель управления**: один и тот же интерфейс автоматически адаптируется под права конкретного пользователя (13 ролей), показывая только доступные ему разделы.

## 2. Архитектура

Платформа построена по классической **клиент-серверной** модели с **монолитным** бэкендом и **SPA-подобным** фронтендом.

```
┌─────────────────────────────────────────────────────────────┐
│                        БРАУЗЕР (PWA)                        │
│  index.html (вход) → dashboard.html (панель)                │
│  api.js · dashboard.js · dashboard-views.js · style.css     │
│  Service Worker (sw.js) · Manifest (manifest.json)          │
└───────────────┬──────────────────────────────┬──────────────┘
                │ HTTP (REST /api/*)           │ WebSocket (Socket.IO)
                ▼                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    СЕРВЕР (Node.js + Express)               │
│  server/server.js  — маршруты, JWT, RBAC, загрузка, PDF      │
│  middleware: cors · express.json · rate-limit · multer      │
│  Socket.IO: realtime-обновления (terminal:join, emitUpdate) │
└───────────────────────────────┬─────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────┐
│              БАЗА ДАННЫХ (SQLite / better-sqlite3)          │
│  server/db/terminal.db  — 10 таблиц, WAL, FK ON             │
└─────────────────────────────────────────────────────────────┘
```

### Поток запроса

1. Пользователь входит через `POST /api/auth` → получает **JWT-токен** (7 дней).
2. Токен сохраняется в `localStorage` (`token`, `user`) и передаётся в заголовке `Authorization: Bearer <token>`.
3. Каждый защищённый эндпоинт проходит через middleware `authRequired` (проверка JWT) и, при необходимости, `roleRequired(...)` (проверка роли).
4. Сервер выполняет операции с SQLite и, для изменяющих операций, рассылает **realtime-события** через Socket.IO всем подключённым клиентам в комнате `terminal`.
5. Фронтенд получает событие и автоматически перерисовывает текущий раздел (если он открыт).

## 3. Технологический стек

| Слой | Технология | Назначение |
|------|-----------|-----------|
| **Бэкенд** | Node.js (≥18), Express 4 | HTTP-сервер, REST API |
| **База данных** | SQLite + better-sqlite3 | Локальная файловая БД (WAL, FK) |
| **Авторизация** | jsonwebtoken (JWT), bcryptjs | Токены и хэширование паролей |
| **Реальное время** | Socket.IO 4 | Живые обновления интерфейса |
| **Защита** | express-rate-limit | Ограничение частоты запросов |
| **Загрузка файлов** | multer 2 | Загрузка фото (до 5 МБ, изображения) |
| **PDF-отчёты** | PDFKit | Генерация отчётов по контейнерам/вагонам |
| **Файловая система** | fs-extra | Создание директории загрузок |
| **Фронтенд** | HTML5, CSS3, Vanilla JS | Без фреймворков, лёгкий и быстрый |
| **PWA** | Service Worker, Web App Manifest | Офлайн-кэш, установка на устройство |
| **Деплой** | Docker, Render (Blueprint), Fly.io | Контейнеризация и облачный хостинг |
| **Тесты** | Node.js smoke + RBAC (112 проверок) | Изолированный прогон на временной БД |

### 5.2 Начальные данные (seed)

При первом запуске `db.js` автоматически создаёт (только если таблицы пусты):

- **13 пользователей** (см. таблицу ролей в разделе 7).
- **4 железнодорожных пути**: Путь №1–2 (Зона А, 25 ваг.), Путь №3–4 (Зона Б, 20 ваг.).
- **4 единицы спецтехники**: Кран КК-1, Кран КК-2, Погрузчик П-1, Тягач Т-1.
- **Склады терминала**: КНС, СПРЕЙДЕР, ППЖТ, Склад №1 (из образцов бумажных форм).
- **Контрагенты**: собственники и получатели контейнеров (ТОО, АО, физлица).
- **Счётчики нумерации** `doc_seq`: завоз продолжается с `06860`, вывоз и накладная — с
  `000004855`, пропуск — с `000020129`.

### 8.12 Завоз и вывоз (документы терминала)

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `GET` | `/api/operations` | все | Журнал документов. Параметры: `kind` (завоз/вывоз), `status`, `q` (номер, контейнер, госномер, водитель) |
| `GET` | `/api/operations/:id` | все | Карточка документа + связанные `pass`, `invoice` и строки накладных |
| `POST` | `/api/operations` | admin, dispatcher, receiver, guard, shift, ppjt | Создать документ (`kind` обязателен, номер — из `doc_seq`) |
| `PATCH` | `/api/operations/:id` | admin, dispatcher, receiver, guard, shift, ppjt | Изменить документ: шапка целиком (`org`, контрагенты, склад, контейнер и категория, `cargo_status`, способ тр-ки, `movement`, `plate`, `driver`, `seal_no`, вагон, ответственный, `comment`, `status`, `ignore_wagon`, `transferred`) |
| `POST` | `/api/operations/:id/pass` | admin, guard, dispatcher, shift | «Ввести пропуск» по документу: пропуск создаётся и связывается с завозом/вывозом |

Особенности:

- Номер документа выдаётся из `doc_seq`: завоз — 5 цифр (`06860`), вывоз — 9 (`000004855`).
- `basis_id` принимается только на **завоз** (вывоз оформляется по завозу, иначе 400).
- Неизвестный статус игнорируется — остаётся текущее значение.
- `PATCH` применяет только переданные поля: `cargo_status` и `transferred` пишутся как есть,
  `transferred` актуален для вывоза (в форме отображается чекбоксом «Передан»).
- `op_date` возвращается и сохраняется со временем (например `17.09.2026 12:21:45`).
- Повторный `POST /api/operations/:id/pass` не создаёт второй пропуск, а возвращает уже выданный (200).
- Документ без госномера пропуск не получает (400).

### 8.13 Расходные накладные

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `GET` | `/api/invoices` | все | Список накладных (со счётчиком и суммой строк); `?full=1` — со строками |
| `GET` | `/api/invoices/:id` | все | Накладная с шапкой и строками |
| `POST` | `/api/invoices` | admin, dispatcher, finance, shift | Создать накладную; строки можно передать сразу массивом `items` |
| `PATCH` | `/api/invoices/:id` | admin, dispatcher, finance, shift | Изменить шапку (получатель, доверенность, статус) |
| `POST` | `/api/invoices/:id/items` | admin, dispatcher, shift | Добавить строку (контейнер, категория, склад подтягиваются из документа завоза) |
| `POST` | `/api/invoices/:id/items/bulk` | admin, dispatcher, shift | «Добавить из отпуска»: пакетно создать строки по отмеченным завозам (`{operation_ids: []}` → `{added}`, повторные завозы пропускаются) |
| `DELETE` | `/api/invoices/:id/items/:itemId` | admin, dispatcher, shift | Удалить строку |
| `POST` | `/api/invoices/:id/items/:itemId/outbound` | admin, dispatcher, shift | «Создать вывоз по текущей строке»: вывоз наследует контейнер, категорию, склад, контрагентов и завоз-основание |

Особенности:

- Шапка правится через `PATCH`: получатель и собственник, «Через кого» (`proxy_no`,
  `proxy_from`, `proxy_to`, `proxy_person`), чекбокс «Физ лицо» (`proxy_individual`),
  `basis_doc`, статус, ответственный, комментарий.
- Все операции со строками и выпуск вывоза из строки доступны ролям admin, dispatcher и shift.

## 9. Реальное время (Socket.IO)

Сервер инициализирует Socket.IO поверх HTTP-сервера с CORS `origin: '*'`.

### События клиент → сервер
- `terminal:join` — клиент входит в общую комнату `terminal` и, при передаче роли, в комнату `role:<роль>`.

### События сервер → клиент (`emitUpdate`)
Сервер рассылает события всем в комнате `terminal`. Фронтенд перерисовывает раздел, только если он сейчас открыт:

| Событие | Триггер | Раздел |
|---------|---------|--------|
| `container:update` | создание/изменение контейнера | Контейнеры |
| `wagon:update` | добавление/изменение вагона | Пути и вагоны |
| `equipment:update` | изменение техники | Спецтехника |
| `vehicle:update` | въезд/выезд транспорта | Транспорт |
| `request:update` | создание/изменение заявки | Заявки |
| `queue:update` | изменение очереди | Очередь |
| `pass:update` | оформление пропуска, в том числе по документу завоза/вывоза | Пропускной режим |
| `barrier:update` | открытие/закрытие шлагбаума | Пропускной режим (индикатор шлагбаума) |
| `operation:update` | создание/изменение завоза, вывоза, пропуск по документу, вывоз из строки накладной | Завоз / Вывоз |
| `invoice:update` | создание накладной, добавление/удаление строки | Расходные накладные |
| `dictionary:update` | изменение складов и контрагентов | Справочники (сброс кэша справочников) |

Модуль [`dashboard-docs.js`](public/js/dashboard-docs.js) переиспользует соединение,
созданное в [`dashboard-views.js`](public/js/dashboard-views.js) (`window.__dashboardSocket`),
чтобы не открывать второе Socket.IO-подключение на страницу.

### 11.2 Service Worker — [`sw.js`](public/sw.js)
- Кэш: `qazconhub-cache-v6` (версия обновляется при изменениях статики).
- **Статические ресурсы** кэшируются при установке: `/`, `index.html`, `dashboard.html`, `style.css`, `api.js`, `dashboard.js`, `dashboard-views.js`, `dashboard-docs.js`, `manifest.json`.
- **Активация**: удаляются все старые кэши (кроме текущего), `clients.claim()`.
- **Стратегия кэширования**:
  - **API и Socket.IO** (`/api`, `/socket.io`) — **не кэшируются** (всегда сеть).
  - **Навигация** — *network-first* с фолбэком на кэш (офлайн-доступ к панели).
  - **Статика** — *cache-first* с фоновым обновлением.
- Версия кэша инкрементируется при каждом изменении статики (сейчас `v6`), что форсирует
  обновление у клиентов — без этого вернувшиеся пользователи получают старый интерфейс
  из cache-first кэша.

## 12. Безопасность

Платформа реализует многоуровневую защиту:

| Мера | Реализация |
|------|-----------|
| **Хэширование паролей** | bcrypt (cost 10) — пароли не хранятся в открытом виде |
| **JWT-авторизация** | Токены со сроком 7 дней, подпись секретным ключом |
| **Ролевой доступ (RBAC)** | `roleRequired(...)` на каждом изменяющем эндпоинте |
| **Rate limiting** | API: 500 запросов/15 мин; вход: 30 попыток/15 мин |
| **XSS-защита** | Экранирование вывода через `esc()` на фронтенде |
| **Аудит действий** | Каждое значимое действие пишется в `audit_log` |
| **Ограничение загрузок** | Только изображения, максимум 5 МБ (multer) |
| **Обработка ошибок** | Централизованный middleware, без утечки деталей |
| **Секреты в окружении** | `JWT_SECRET` через `.env` (не в коде) |

### Ключевые middleware-защиты

- **`authRequired`** — проверяет заголовок `Authorization: Bearer <token>`, расшифровывает JWT и кладёт `req.user`. При недействительном токене — `401`.
- **`roleRequired(...roles)`** — проверяет, что роль `req.user.role` входит в разрешённый список. Иначе — `403`.
- **`apiLimiter`** — глобальный лимит на все `/api`-запросы.
- **`authLimiter`** — усиленный лимит на эндпоинт входа (защита от brute-force).

Сервер доступен на `http://localhost:8080`. База данных `server/db/terminal.db` создаётся автоматически при первом запуске вместе с демо-данными.

### 13.5 Render (Blueprint)

[`render.yaml`](render.yaml:1) описывает сервис как код: тип `web`, runtime `docker`, план `free`,
регион `frankfurt`, health-check `/`, `autoDeploy: true`.

- `JWT_SECRET` генерируется Render автоматически (`generateValue: true`), `NODE_ENV=production` задаётся в манифесте.
- В репозитории несколько проектов: разворачивать нужно ветку **`qazconhub`**, а не `master`, иначе Render не найдёт Blueprint.
- При пуше в ветку `qazconhub` сервис пересобирается автоматически; интерфейс обновляется у клиентов после поднятия версии кэша в [`public/sw.js`](public/sw.js:1).
- Бесплатный тариф: сервис засыпает после 15 минут простоя (холодный старт 30–60 с), файловая система эфемерная — БД пересоздаётся вместе с seed-данными при каждом перезапуске, для постоянного хранения нужен платный Disk.

Подробная пошаговая инструкция — в [`DEPLOY.md`](DEPLOY.md:1).

## 14. Тестирование и проверка

### 14.1 API-тесты — [`api-test.js`](test/api-test.js)

```bash
npm test        # изолированно: run-isolated.sh поднимает сервер на :8099 с временной БД в /tmp
```

Тест создаёт записи и не удаляет их за собой, поэтому прямой запуск против рабочей БД
(`server/db/terminal.db`, порт :8080) блокируется fail-fast проверкой в начале
[`api-test.js`](test/api-test.js:46). Другие режимы:

```bash
BASE_URL=https://<хост> npm run test:direct     # против внешнего стенда
ALLOW_DIRTY_DB=1 npm run test:direct            # осознанно в рабочую БД
npm run db:clean-test                           # dry-run: показать артефакты тестов
npm run db:clean-test -- --apply                # удалить их (с бэкапом terminal.db)
```

**112 проверок, все зелёные.** Что покрывается:

- Авторизация: вход под всеми ролями, отказ при неверном пароле и без токена.
- Все модули: контейнеры, пути, вагоны, техника, транспорт, заявки, очередь, пропуска,
  OCR/шлагбаум, отчёты (PDF), загрузка фото.
- **Документооборот**: нумерация (`06860`, `000004855`, `000020129`), карточка завоза с
  фильтрами и поиском, поля `cargo_status` и `transferred` (включая отметку «Передан» через
  `PATCH`), пропуск по документу (повторный вызов идемпотентен), накладная со строками,
  подтягивание контейнера/категории/склада из завоза, пакетный подбор строк
  `/items/bulk` (повторные завозы пропускаются), «создать вывоз по строке».
- **RBAC**: 20+ негативных проверок (client, driver, guard, finance не могут того, что
  не входит в их права) и позитивные проверки доступов.
- Валидации: неизвестный `kind` или неизвестная роль контрагента не ломают документ
  (подставляются безопасные значения), дубликат склада → 409.

### 14.2 Браузерная проверка (Playwright)

| Размер | Проверка |

Проверены сценарии:
- Вход под разными ролями (admin — 14 разделов, guard — 4 раздела).
- Открытие/закрытие мобильного меню (кнопка, пункт меню, Escape, оверлей, свайпы).
- Блокировка/разблокировка прокрутки тела при открытом меню.
- Разделы **Завоз**, **Вывоз**, **Расходные накладные**, **Справочники**: реестры, фильтры,
  формы создания документа и накладной со строками, карточка документа с кнопкой «Ввести пропуск».

  Закрыть» остаются на экране при прокрутке длинной формы (в т.ч. на 375px — столбиком).

- Отсутствие ошибок в консоли браузера.

### 14.3 Гигиена данных — [`cleanup-test-data.js`](tools/cleanup-test-data.js)

Автотесты пишут в БД, поэтому появился инструмент точечной очистки рабочих данных:

```bash
npm run db:clean-test              # dry-run: печатает, что будет удалено
npm run db:clean-test -- --apply   # удалить (сначала делает бэкап terminal.db)
```

Правила поиска: контейнеры `TEST*`, вагоны `WAG*`, техника/склады/пути/контрагенты с
префиксами «ТЕСТ-», пропуска `P*` и очередь `Q*`/`D*`/`T*`, заявки `REQ*`, документы,
созданные после 15.09.2026 (дата появления первого прогона), и записи журнала `audit_log`,
относящиеся к удалённым сущностям. После удаления счётчики `doc_seq` откатываются к
последнему «настоящему» номеру, поэтому следующие документы получают номера без дыр.
Бэкап (`server/db/terminal.db.bak-<время>`) позволяет откатиться, если что-то было
удалено лишнее.

## 16. Заключение

**QazconHub** — полнофункциональная, готовая к эксплуатации PWA-платформа управления логистическим терминалом. Она объединяет в едином адаптивном интерфейсе все ключевые операционные процессы: от учёта контейнеров и вагонов до пропускного режима с OCR и электронной очереди, а также полный документооборот терминала — завоз и вывоз по бумажным формам, расходные накладные со строками и справочники складов и контрагентов. Благодаря ролевой модели (13 ролей), realtime-синхронизации через Socket.IO, PWA-возможностям (офлайн, установка) и адаптивному дизайну (мобильные/планшетные/десктопные экраны) платформа пригодна для использования как на стационарных рабочих местах терминала, так и в полевых условиях сотрудниками, клиентами и водителями.

Качество подтверждается автотестами: 112 проверок API (авторизация, RBAC по 13 ролям, все модули, документооборот и справочники) выполняются в изолированном окружении — свой сервер на порту :8099 и временная БД в `/tmp`, поэтому рабочая база не загрязняется. Дополнительно есть инструмент очистки рабочей БД от артефактов прогонов ([`tools/cleanup-test-data.js`](tools/cleanup-test-data.js:1)) с бэкапом и откатом счётчиков нумерации `doc_seq`.
