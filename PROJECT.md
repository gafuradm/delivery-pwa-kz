# 📘 QazconHub — Детальное документ-описание проекта

> **Полное техническое описание** цифровой платформы логистического терминала ТОО «QazconHub».
> Документ охватывает архитектуру, стек технологий, схему базы данных, все API-эндпоинты, ролевую модель, структуру фронтенда, PWA-возможности, безопасность и развёртывание.

---

## 1. Обзор проекта

**QazconHub** — это современное **PWA-приложение** (Progressive Web App) для комплексного управления логистическим терминалом. Платформа автоматизирует ключевые операционные процессы терминала:

- 📦 **Контейнерные операции** — учёт, размещение и отслеживание контейнеров.
- 🚂 **Железнодорожные пути (ППЖТ)** — управление путями и вагонами.
- 🏗️ **Спецтехника** — учёт кранов, погрузчиков и тягачей.
- 🚛 **Транспорт и пропускной режим** — въезд/выезд, OCR-распознавание номеров, шлагбаумы, пропуска.
- 🔢 **Электронная очередь** — запись водителей и назначение слотов.
- 📋 **Заявки клиентов** — создание и обработка заявок.
- 📜 **Журнал действий и отчёты** — аудит и PDF-отчёты.

Ключевая особенность — **единая роль-ориентированная панель управления**: один и тот же интерфейс автоматически адаптируется под права конкретного пользователя (13 ролей), показывая только доступные ему разделы.

## 2. Архитектура

Платформа построена по классической **клиент-серверной** модели с **монолитным** бэкендом и **SPA-подобным** фронтендом.

```
┌─────────────────────────────────────────────────────────────┐
│                        БРАУЗЕР (PWA)                        │
│  index.html (вход) → dashboard.html (панель)                │
│  api.js · dashboard.js · dashboard-views.js · style.css     │
│  Service Worker (sw.js) · Manifest (manifest.json)          │
└───────────────┬──────────────────────────────┬──────────────┘
                │ HTTP (REST /api/*)           │ WebSocket (Socket.IO)
                ▼                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    СЕРВЕР (Node.js + Express)               │
│  server/server.js  — маршруты, JWT, RBAC, загрузка, PDF      │
│  middleware: cors · express.json · rate-limit · multer      │
│  Socket.IO: realtime-обновления (terminal:join, emitUpdate) │
└───────────────────────────────┬─────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────┐
│              БАЗА ДАННЫХ (SQLite / better-sqlite3)          │
│  server/db/terminal.db  — 10 таблиц, WAL, FK ON             │
└─────────────────────────────────────────────────────────────┘
```

### Поток запроса

1. Пользователь входит через `POST /api/auth` → получает **JWT-токен** (7 дней).
2. Токен сохраняется в `localStorage` (`token`, `user`) и передаётся в заголовке `Authorization: Bearer <token>`.
3. Каждый защищённый эндпоинт проходит через middleware `authRequired` (проверка JWT) и, при необходимости, `roleRequired(...)` (проверка роли).
4. Сервер выполняет операции с SQLite и, для изменяющих операций, рассылает **realtime-события** через Socket.IO всем подключённым клиентам в комнате `terminal`.
5. Фронтенд получает событие и автоматически перерисовывает текущий раздел (если он открыт).

## 3. Технологический стек

| **Фронтенд** | HTML5, CSS3, Vanilla JS | Без фреймворков, лёгкий и быстрый |

| **Деплой** | Docker, Fly.io | Контейнеризация и облачный хостинг |

## 8. API-эндпоинты (REST)

Базовый URL: `/api`. Все эндпоинты, кроме `POST /api/auth`, требуют заголовок `Authorization: Bearer <JWT>`.

### 8.1 Аутентификация и справочники

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `POST` | `/api/auth` | — (публичный, rate-limit 30/15мин) | Вход: `{login, pass}` → `{token, user}` |
| `GET` | `/api/roles` | все | Справочник ролей (код → название) |
| `GET` | `/api/stats` | все | Сводная статистика терминала |

**`GET /api/stats`** возвращает: `containers`, `containersFull`, `wagons`, `wagonsOnTrack`, `equipment`, `eqFree`, `vehicles`, `queue`, `requestsNew`.

### 8.2 Контейнеры

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `GET` | `/api/containers` | все | Список контейнеров |
| `POST` | `/api/containers` | admin, dispatcher, receiver, guard, shift | Создать контейнер |
| `PATCH` | `/api/containers/:id` | admin, dispatcher, receiver, crane, shift | Обновить (статус, размещение, клиент, груз, вес) |

### 8.3 Пути (ППЖТ)

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `GET` | `/api/tracks` | все | Пути + вагоны на них + заполненность |
| `POST` | `/api/tracks` | admin, ppjt | Создать путь |

### 8.4 Вагоны

| Метод | Путь | Роли | Описание |
|-------|------|------|----------|
| `GET` | `/api/wagons` | все | Список вагонов (с названием пути) |
| `POST` | `/api/wagons` | admin, ppjt, receiver | Добавить вагон (прибытие) |
| `PATCH` | `/api/wagons/:id` | admin, ppjt, receiver, shift | Обновить (путь, статус, направление, станция) |

### 8.5 Спецтехника

| Метод | Путь | Роли | Описание |

## 9. Реальное время (Socket.IO)

Сервер инициализирует Socket.IO поверх HTTP-сервера с CORS `origin: '*'`.

### События клиент → сервер
- `terminal:join` — клиент входит в общую комнату `terminal` и, при передаче роли, в комнату `role:<роль>`.

### События сервер → клиент (`emitUpdate`)
Сервер рассылает события всем в комнате `terminal`. Фронтенд перерисовывает раздел, только если он сейчас открыт:

| Событие | Триггер | Раздел |
|---------|---------|--------|
| `container:update` | создание/изменение контейнера | Контейнеры |
| `wagon:update` | добавление/изменение вагона | Пути и вагоны |
| `equipment:update` | изменение техники | Спецтехника |
| `vehicle:update` | въезд/выезд транспорта | Транспорт |
| `request:update` | создание/изменение заявки | Заявки |
| `queue:update` | изменение очереди | Очередь |
| `barrier:update` | открытие/закрытие шлагбаума | Пропускной режим |

## 11. PWA (Progressive Web App)

### 11.1 Манифест — [`manifest.json`](public/manifest.json)
- `name`: «QazconHub — Логистический терминал», `short_name`: «QazconHub».
- `display: standalone`, `theme_color: #0f2a4a`, `background_color: #f0f4f8`.
- Иконки 192×192 и 512×512 (`icon.png`, `purpose: any maskable`).
- `start_url: /`, `lang: ru`.

### 11.2 Service Worker — [`sw.js`](public/sw.js)
- Кэш: `qazconhub-cache-v2` (версия обновляется при изменениях статики).
- **Статические ресурсы** кэшируются при установке: `/`, `index.html`, `dashboard.html`, `style.css`, `api.js`, `dashboard.js`, `dashboard-views.js`, `manifest.json`.
- **Активация**: удаляются все старые кэши (кроме текущего), `clients.claim()`.
- **Стратегия кэширования**:
  - **API и Socket.IO** (`/api`, `/socket.io`) — **не кэшируются** (всегда сеть).
  - **Навигация** — *network-first* с фолбэком на кэш (офлайн-доступ к панели).
  - **Статика** — *cache-first* с фоновым обновлением.
- Версия кэша инкрементируется при каждом изменении статики (сейчас `v2`), что форсирует обновление у клиентов.

## 12. Безопасность

Платформа реализует многоуровневую защиту:

| Мера | Реализация |
|------|-----------|
| **Хэширование паролей** | bcrypt (cost 10) — пароли не хранятся в открытом виде |
| **JWT-авторизация** | Токены со сроком 7 дней, подпись секретным ключом |
| **Ролевой доступ (RBAC)** | `roleRequired(...)` на каждом изменяющем эндпоинте |
| **Rate limiting** | API: 500 запросов/15 мин; вход: 30 попыток/15 мин |
| **XSS-защита** | Экранирование вывода через `esc()` на фронтенде |
| **Аудит действий** | Каждое значимое действие пишется в `audit_log` |
| **Ограничение загрузок** | Только изображения, максимум 5 МБ (multer) |
| **Обработка ошибок** | Централизованный middleware, без утечки деталей |
| **Секреты в окружении** | `JWT_SECRET` через `.env` (не в коде) |

### Ключевые middleware-защиты

- **`authRequired`** — проверяет заголовок `Authorization: Bearer <token>`, расшифровывает JWT и кладёт `req.user`. При недействительном токене — `401`.
- **`roleRequired(...roles)`** — проверяет, что роль `req.user.role` входит в разрешённый список. Иначе — `403`.
- **`apiLimiter`** — глобальный лимит на все `/api`-запросы.
- **`authLimiter`** — усиленный лимит на эндпоинт входа (защита от brute-force).

## 13. Развёртывание

### 13.1 Локальный запуск

```bash
# Установка зависимостей
npm install

# Настройка окружения (опционально)
cp .env.example .env

# Запуск сервера (порт 8080)
npm start
```

Сервер доступен на `http://localhost:8080`. База данных `server/db/terminal.db` создаётся автоматически при первом запуске вместе с демо-данными.

### 13.2 Переменные окружения (`.env`)

| Переменная | По умолчанию | Описание |
|-----------|-------------|----------|
| `JWT_SECRET` | `qazconhub-terminal-secret-change-in-prod` | Секрет подписи JWT (**обязательно сменить в проде**) |
| `PORT` | `8080` | Порт HTTP-сервера |

### 13.3 Docker

[`Dockerfile`](Dockerfile) собирает образ на базе `node:20-alpine`:

```bash
docker build -t qazconhub-terminal .
docker run -p 8080:8080 qazconhub-terminal
```

Особенности:
- Устанавливаются инструменты сборки (`python3 make g++`) для нативного модуля `better-sqlite3`.
- `npm install --production` — только продакшен-зависимости.
- Создаётся директория `public/uploads`.
- `NODE_ENV=production`, порт `8080`.

### 13.4 Fly.io

[`fly.toml`](fly.toml) — конфигурация облачного деплоя:

```bash
fly launch
fly deploy
```

Конфигурация: приложение `qazconhub-terminal`, регион `ams`, HTTP-сервис на порту `8080` с `force_https`, авто-стоп/старт машин, 1 виртуальная машина (512 МБ RAM, 1 CPU).

## 16. Заключение

**QazconHub** — полнофункциональная, готовая к эксплуатации PWA-платформа управления логистическим терминалом. Она объединяет в едином адаптивном интерфейсе все ключевые операционные процессы: от учёта контейнеров и вагонов до пропускного режима с OCR и электронной очереди. Благодаря ролевой модели (13 ролей), realtime-синхронизации через Socket.IO, PWA-возможностям (офлайн, установка) и адаптивному дизайну (мобильные/планшетные/десктопные экраны) платформа пригодна для использования как на стационарных рабочих местах терминала, так и в полевых условиях сотрудниками, клиентами и водителями.
